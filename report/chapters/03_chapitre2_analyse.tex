Les solutions existantes présentent plusieurs limitations :
\begin{itemize}
    \item \textbf{Personnalisation limitée :} La plupart des outils offrent des modèles fixes sans adaptation réelle au contenu de l'offre d'emploi.
    \item \textbf{Absence de suivi intégré :} Aucune solution ne combine la génération de CV avec le suivi des candidatures dans une plateforme unifiée.
    \item \textbf{Coût :} Les solutions avancées sont payantes (abonnements mensuels).
    \item \textbf{Optimisation ATS limitée :} Peu d'outils optimisent réellement le CV pour passer les filtres des systèmes ATS.
\end{itemize}

\projectname{} se distingue en offrant une solution complète, gratuite et open source, combinant génération IA de CV, optimisation ATS et suivi de candidatures.

\section{Étude des besoins non fonctionnels}
\label{sec:analyse:non-fonctionnels}

Les besoins non fonctionnels identifiés sont :

\begin{itemize}
    \item \textbf{Performance :} La génération d'un CV ne doit pas excéder quelques secondes. Les temps de réponse de l'API doivent être optimisés.
    \item \textbf{Sécurité :} L'authentification doit être centralisée via Keycloak avec support OAuth2 et OpenID Connect. Les communications doivent être chiffrées (HTTPS). Les vulnérabilités doivent être scannées via Trivy et OWASP ZAP.
    \item \textbf{Disponibilité :} Le système doit être résilient grâce à une architecture en microservices et une orchestration Docker. Les services critiques doivent pouvoir redémarrer automatiquement.
    \item \textbf{Maintenabilité :} Le code source doit être organisé en modules séparés, versionné avec Git, et suivre les principes SOLID. La qualité du code est surveillée via SonarCloud.
    \item \textbf{Évolutivité :} L'architecture microservices permet de faire évoluer chaque service indépendamment. L'utilisation de Kafka permet un couplage faible entre les services.
    \item \textbf{Ergonomie :} L'interface utilisateur doit être intuitive, responsive et suivre une charte graphique cohérente (design system Propel).
    \item \textbf{Portabilité :} L'ensemble de l'application doit être conteneurisée avec Docker pour garantir un déploiement reproductible sur n'importe quel environnement.
\end{itemize}

\subsection{Diagramme de séquence — Flux d'authentification}
\label{subsec:analyse:sequence}

Le diagramme de séquence ci-dessous illustre le flux d'authentification via Keycloak avec le protocole OpenID Connect (OIDC). L'utilisateur est redirigé vers Keycloak pour s'authentifier, reçoit un code d'autorisation, puis l'API Gateway échange ce code contre des jetons JWT. Un cookie de session (\texttt{cv\_session}) est créé pour maintenir la session. Lors de l'inscription, un événement \texttt{user.registered} est publié sur Kafka pour notifier les autres services.

\subsection{Modèle relationnel de la base de données}
\label{subsec:analyse:bdd}

L'architecture microservices du projet implique l'utilisation de plusieurs bases de données PostgreSQL 16, une par service. Chaque base de données est spécialisée pour les besoins de son service. L'extension pgvector est utilisée pour le support des recherches vectorielles dans les bases concernées par le pipeline IA.

\subsubsection*{Base Utilisateurs (user-db)}
\label{subsubsec:bdd:user}

La base utilisateurs centralise les informations personnelles et professionnelles des candidats. Elle contient une table principale \texttt{users} qui stocke le profil complet de chaque utilisateur : nom, email, titre professionnel, prétentions salariales, préférences de localisation, et données JSON pour le profil IA.

\begin{figure}[H]
\centering
\includegraphics[width=0.8\textwidth]{images/user-db.png}
\caption{Modèle relationnel — Base Utilisateurs}
\label{fig:user-db}
\end{figure}

\subsubsection*{Base Contenu Utilisateur (content-db)}
\label{subsubsec:bdd:content}

Cette base gère l'ensemble du portfolio utilisateur. Elle contient 11 tables permettant de gérer les projets, compétences, expériences professionnelles, formations, certifications, langues, centres d'intérêt, hackathons, liens sociaux, profils CV et activités académiques. Chaque table est reliée à un utilisateur via une clé étrangère \texttt{userId}.

\label{subsubsec:bdd:application}

La base candidatures assure le suivi des candidatures des utilisateurs. Elle est composée de trois tables : \texttt{applications} (candidatures avec statut, entreprise, poste), \texttt{applicationStatusHistory} (historique des changements de statut) et \texttt{applicationConfigurations} (préférences de l'utilisateur pour le module).

\subsubsection*{Base Workflow (workflow-db)}
\label{subsubsec:bdd:workflow}

La base workflow est la plus complexe, car elle pilote le pipeline de génération de CV. Elle contient les tables \texttt{workflows} (définition des pipelines), \texttt{cvGenerationRuns} (traces d'exécution avec résultats de chaque étape), \texttt{agents} (configuration des agents IA), \texttt{agentDocumentChunks} (documents vectorisés pour le RAG), \texttt{jobExtractions} (extractions d'offres), ainsi que des entités miroir du contenu utilisateur optimisées pour la recherche vectorielle : \texttt{workflowProjects}, \texttt{workflowSkills} et \texttt{workflowExperiences}.
