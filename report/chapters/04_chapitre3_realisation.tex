La répartition des VMs est la suivante :
\begin{itemize}

    \item \textbf{Somia (2 VMs) :} Service Workflow avec base pgvector, Agents IA (Optimizer, Search, Crawler).
    \item \textbf{Nourelhouda (1 VM) :} Infrastructure transverse (Keycloak, Kafka, MinIO).
    \item \textbf{Mouhssine (1 VM) :} Service CV et Service Offres d'Emploi.
    \item \textbf{Salman (1 VM) :} Monitoring (Prometheus, Grafana).
\end{itemize}

Chaque VM dispose de 2 CPU et 2 Go de RAM, et les services communiquent entre VMs via le réseau partagé Docker.

\subsubsection{Environnement de déploiement}
\label{subsubsec:realisation:deploiement}

L'ensemble de l'application est conteneurisé à l'aide de \textbf{Docker}. Chaque service possède son propre Dockerfile avec une construction multi-stage optimisée. L'orchestration est assurée par \textbf{Docker Compose} au niveau racine du projet, qui inclut trois fichiers compose spécialisés :

\begin{itemize}
    \item \textbf{backend/docker-compose.yml :} Contient les 7 microservices backend .NET, les 8 bases de données PostgreSQL, Kafka, et MinIO.
    \item \textbf{ai\_agents/docker-compose.yml :} Contient le pipeline de 6 agents IA en Python avec leur orchestrateur.

\end{itemize}

Tous les services partagent un réseau Docker commun (\texttt{cv-network}) pour la communication inter-services.

\subsection{Architecture logicielle}
\label{subsec:realisation:archi-logicielle}

L'architecture logicielle de \projectname{} est une architecture en \textbf{microservices} avec communication événementielle. Le schéma ci-dessous illustre l'architecture globale du système.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{images/system-architecture.png}
\caption{Architecture logicielle du système}
\label{fig:archi-logicielle}
\end{figure}

L'architecture se compose des couches suivantes :

\begin{itemize}
    \item \textbf{Frontend (Angular)} : Application monopage (SPA) hébergée par Nginx, consommant l'API via la passerelle.
    \item \textbf{Passerelle API (YARP)} : Proxy inverse .NET assurant le routage, l'authentification et la gestion des sessions. Publie les événements de connexion vers Kafka.
    \item \textbf{Backend (.NET)} : 7 microservices indépendants, chacun avec sa propre base de données PostgreSQL. Ils communiquent via HTTP, gRPC et Kafka.
    \item \textbf{Agents IA (Python)} : Pipeline de 6 agents FastAPI utilisant LangChain et LangGraph pour le traitement intelligent des CV.
    \item \textbf{Messagerie (Kafka)} : Système de messagerie asynchrone en mode KRaft (sans Zookeeper) pour la communication événementielle entre services.
    \item \textbf{Stockage objet (MinIO)} : Stockage S3-compatible pour les fichiers PDF générés.
    \item \textbf{Authentification (Keycloak)} : Serveur d'authentification centralisé avec support OAuth2, OpenID Connect et fédération d'identités (Google, GitHub).
\end{itemize}

\section{Cycle DevSecOps}
\label{sec:realisation:devsecops}

\subsection{Présentation et importance dans le projet}
\label{subsec:realisation:devsecops-presentation}

Le cycle DevSecOps intègre la sécurité à chaque étape du cycle de développement logiciel. Dans le cadre de \projectname{}, cette approche est essentielle étant donné la nature sensible des données traitées (informations personnelles des utilisateurs, CV, données de connexion).

L'adoption du cycle DevSecOps nous permet de :
\begin{itemize}
    \item Détecter les vulnérabilités tôt dans le cycle de développement.
    \item Automatiser les contrôles de sécurité.
    \item Garantir la conformité aux bonnes pratiques.
    \item Assurer une traçabilité complète des modifications.
\end{itemize}

\subsection{Outils DevSecOps utilisés}
\label{subsec:realisation:devsecops-outils}

\begin{itemize}
    \item \textbf{SonarCloud :} Analyse statique de code avec quality gates pour les projets Angular, .NET et Python. Des seuils de qualité (couverture de code, dette technique, duplication) doivent être respectés.
    \item \textbf{Trivy :} Scan de vulnérabilités sur le système de fichiers lors des phases statiques et sur les images Docker construites. Détection des dépendances obsolètes et des failles de sécurité connues.
    \item \textbf{OWASP ZAP :} Tests DAST (Dynamic Application Security Testing) en environnement d'intégration pour détecter les vulnérabilités applicatives (XSS, injection SQL, etc.).
\end{itemize}

\subsection{Application du cycle DevSecOps dans le projet}
\label{subsec:realisation:devsecops-application}

Le cycle DevSecOps est appliqué à travers le pipeline CI/CD en six phases :

\begin{enumerate}
    \item \textbf{Phase 1 - Static Checks :} Validation des fichiers Docker Compose, scan Trivy filesystem, analyse SonarCloud pour le frontend, le backend et les agents IA.
    \item \textbf{Phase 2 - Component Tests :} Exécution des tests unitaires (.NET avec xUnit, Angular avec Vitest, Python avec pytest) et génération des rapports de couverture.
    \item \textbf{Phase 3 - Integration / E2E :} Tests d'intégration et tests E2E avec Cypress, suivis d'un scan de sécurité OWASP ZAP.
    \item \textbf{Phase 4 - Build \& Scan :} Construction des images Docker multi-stage, suivie d'un scan Trivy des images.
    \item \textbf{Phase 5 - Registry Push :} Publication des images validées vers GitHub Container Registry et DockerHub.
    \item \textbf{Phase 6 - Deploy :} Déploiement de l'application sur l'environnement cible.
\end{enumerate}

\subsection{Sécurité applicative}
\label{subsec:realisation:securite}

La sécurité applicative est assurée à plusieurs niveaux :

\begin{itemize}
    \item \textbf{Authentification centralisée :} Keycloak avec OpenID Connect, support OAuth2 (Google, GitHub), gestion des sessions par cookies sécurisés JWT.
    \item \textbf{Protection des API :} Validation des tokens JWT, gestion des rôles et permissions.
    \item \textbf{Sécurisation des communications :} HTTPS, chiffrement des données sensibles.
    \item \textbf{Scan de vulnérabilités :} Automatisé via Trivy (images et dépendances) et OWASP ZAP (tests dynamiques).
    \item \textbf{Gestion des secrets :} Fichier \texttt{.env} avec variables d'environnement, exclusion des secrets du versionnement via \texttt{.gitignore}.
\end{itemize}

\subsection{Développement Backend}
\label{subsec:realisation:backend}

Le backend est composé de 7 microservices .NET, chacun responsable d'un domaine métier spécifique :

\begin{itemize}
    \item \textbf{User Service :} Gestion des utilisateurs, synchronisation avec Keycloak, communication gRPC.
    \item \textbf{User Content Service :} Gestion du portfolio (projets, compétences, expériences, formations, certifications, langues).
    \item \textbf{CV Service :} Création et versionnement des CV, gestion des templates, export PDF.
    \item \textbf{Workflow Service :} Orchestration de la génération de CV, appel aux agents IA.
    \item \textbf{Application Service :} Suivi des candidatures, communication gRPC avec User Service.
    \item \textbf{Job Offer Service :} Gestion des offres d'emploi, déclenchement du crawling, hub SignalR.
    \item \textbf{Notification Service :} Envoi d'emails (MailKit), rappels planifiés (Hangfire), consommateur Kafka.
\end{itemize}

La passerelle API (\textbf{YARP}) est un service .NET dédié qui agit comme point d'entrée unique. Elle gère l'authentification, le routage vers les microservices et la publication d'événements Kafka.

\subsubsection{Tests unitaires des agents IA — pytest}
\label{subsubsec:realisation:tests-agents}

L'agent de contact (\texttt{contact-agent}) dispose d'une suite de \textbf{43 tests pytest} répartis en quatre modules :

\begin{itemize}
    \item \textbf{test\_tools.py (19 tests) :} Teste les quatre outils LangGraph de l'agent de manière indépendante.
    \begin{itemize}
        \item \texttt{extract\_cv\_text} — 8 cas : tri par ordre de section, liste vide, JSON invalide, sections sans contenu, présence de plusieurs sections, champs \texttt{order} manquants, contenu avec espaces, section unique.
        \item \texttt{generate\_email\_subject} — 2 cas : retour d'un objet ligne d'objet, vérification que le prompt contient bien les informations de l'offre (LLM mocké via \texttt{unittest.mock}).
        \item \texttt{generate\_email\_body} — 3 cas : retour du corps de l'email, présence de toutes les entrées dans le prompt, gestion d'un \texttt{hint} vide.
        \item \texttt{send\_email\_with\_cv} — 6 cas : envoi réussi sans PDF, identifiants manquants, échec d'authentification SMTP, envoi avec URL PDF valide, échec de téléchargement PDF, fichier PDF local introuvable (SMTP mocké via \texttt{smtplib}).
    \end{itemize}

    \item \textbf{test\_agent.py (7 tests) :} Teste l'orchestration LangGraph de la fonction \texttt{deliver\_cv()}.
    \begin{itemize}
        \item \texttt{deliver\_cv()} — 4 cas : livraison réussie, livraison échouée, génération de l'ID de livraison lorsqu'absent, gestion d'une URL PDF nulle.
        \item \texttt{\_extract\_tool\_output()} — 3 cas : recherche d'un outil par nom, retour de \texttt{N/A} si introuvable, suppression des espaces.
    \end{itemize}

    \item \textbf{test\_schemas.py (12 tests) :} Valide les schémas Pydantic \texttt{ContactInput} et \texttt{ContactOutput}.
    \begin{itemize}
        \item \texttt{ContactInput} — 8 cas : entrée valide, avec \texttt{cover\_letter\_hint}, avec URL PDF, champs obligatoires manquants (\texttt{job\_title}, \texttt{recipient\_email}, \texttt{optimized\_cv}), sections CV vides, valeurs limites du score ATS (0, 100, $-1$, 101).
        \item \texttt{ContactOutput} — 4 cas : sortie réussie, sortie échouée, génération automatique de \texttt{sent\_at}, champ \texttt{delivery\_id} manquant.
    \end{itemize}

    \item \textbf{test\_integration.py (5 tests) :} Teste l'endpoint FastAPI \texttt{/deliver} via le client ASGI (agent mocké).
    \begin{itemize}
        \item 4 tests avec agent mocké : succès, échec, erreur de validation (422), et endpoint \texttt{/health}.
        \item 1 test live (marqué \texttt{@pytest.mark.live}, exécuté uniquement avec \texttt{--run-live}) : envoi réel d'un email de démonstration.
    \end{itemize}
\end{itemize}

\subsection{Tests de Performance — k6}
\label{subsec:realisation:tests-performance}

Les tests de performance mesurent le comportement du système sous charge pour détecter les goulots d'étranglement avant la mise en production.

\subsubsection{Infrastructure et configuration}
\label{subsubsec:realisation:perf-infra}

L'outillage repose sur \textbf{k6} (Grafana) avec une architecture modulaire :

\begin{itemize}
    \item \textbf{config/env.js :} Centralise l'URL de base (\texttt{http://localhost:8080} par défaut, configurable via \texttt{BASE\_URL}), la carte des endpoints et les identifiants de l'utilisateur seedé (\texttt{testuser/test1234}).
    \item \textbf{lib/helpers.js :} Fournit \texttt{buildUser(runId, vu, iter)} pour générer des emails uniques par VU et itération (\texttt{perf\_\{timestamp\}\_v\{vu\}\_i\{iter\}@cvgen-loadtest.local}), ainsi que les en-têtes JSON communs.
    \item \textbf{lib/auth.js :} Fournit \texttt{loginAs(email, password)} qui effectue \texttt{POST /api/auth/login} et maintient le cookie de session par VU pour les scénarios authentifiés.
\end{itemize}

L'infrastructure de test utilise une \textbf{base de données de test dédiée} et un \textbf{realm Keycloak isolé} pour ne pas polluer les données de développement.

\subsubsection{Scénarios de charge}
\label{subsubsec:realisation:perf-scenarios}

Six scénarios couvrent les chemins critiques de l'application :

\midrule

\bottomrule

Les scénarios ont été conçus pour tester des aspects différents :

\begin{itemize}
    \item \textbf{register.js :} Mesure la latence de création d'utilisateur dans Keycloak et la publication de l'événement Kafka vers le User Service.
    \item \textbf{login.js :} Mesure le débit du token endpoint Keycloak sous charge concurrente (50 connexions partagées entre 10 VUs).
    \item \textbf{me.js :} Mesure la performance du chemin de validation de cookie sans appel en amont (seuil le plus strict : p95 < 500ms).
    \item \textbf{applications-list.js :} Mesure la planification de requêtes SQL complexes avec combinaisons aléatoires de filtres (\texttt{statuses}, \texttt{search}, \texttt{appliedFrom}, \texttt{appliedTo}) — permet de détecter les index manquants.
    \item \textbf{cvprofiles-create.js :} Mesure la latence d'écriture PostgreSQL combinée à la publication Kafka — permet d'isoler le goulot d'étranglement par comparaison avec \texttt{register.js}.
    \item \textbf{journey.js :} Exécute le parcours utilisateur complet (inscription → connexion → validation de session → création de profil CV → liste de candidatures) en parallèle sur 10 VUs. Ce scénario révèle les problèmes d'intégration invisibles aux tests d'endpoint unique : lag du consommateur Kafka, problèmes de cookie \texttt{SameSite}, et désynchronisation d'état entre services.
\end{itemize}

Chaque scénario définit des \textbf{métriques personnalisées k6} (\texttt{Rate} et \texttt{Counter}) pour le taux de succès et les erreurs par catégorie (4xx, 5xx, conflits), permettant une analyse fine des résultats.
